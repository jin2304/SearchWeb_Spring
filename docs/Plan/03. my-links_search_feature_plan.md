# My Links 검색 기능 계획서

> **문서 정보**
> - **버전:** v0.1.0 (Draft)
> - **작성일:** 2026-04-14
> - **관련 화면:** `/my-links`
> - **관련 문서:** [SearchWeb PRD](./01.%20searchweb_PRD.md), [KPI 측정 설계](./02.%20kpi_measurement_design.md), [Frontend Architecture](../Fontend/01.%20frontend_architecture.md)
> - **문서 목적:** `/my-links` 검색 기능의 UX 정책, 결과 구조, 데이터 규칙, 구현 범위를 정의한다.

<br>

## 1. 개요

`/my-links` 화면은 현재 좌측 메인 영역과 우측 링크 패널의 역할이 분리되어 있다.

- 좌측 메인 영역: 폴더 탐색, 폴더 생성, 전체 구조 탐색
- 우측 패널: 선택된 폴더 기준 링크 조회, 정렬, 태그 필터, 링크 편집

검색 기능 역시 이 역할 분리를 유지하면서도, 사용자는 일관된 검색 경험을 느낄 수 있어야 한다.  
따라서 본 계획서는 다음 원칙을 채택한다.

- **검색 경험은 통일한다.**
- **검색 범위와 결과 해석은 영역별로 분리한다.**
- **전체검색에서는 폴더와 링크를 모두 보여주되, 결과를 섞지 않고 섹션으로 분리한다.**
- **링크가 여러 폴더에 저장된 경우, 포함된 폴더 정보를 명시적으로 보여준다.**

<br>

## 2. 문제 정의

현재 `/my-links` 상단에는 `Search folders or links` 형태의 입력창이 존재하지만, 실제 검색 범위와 결과 정책은 정의되어 있지 않다.

이 상태에서 검색을 바로 구현하면 다음 문제가 생길 수 있다.

- 사용자가 지금 찾는 대상이 폴더인지 링크인지 명확하지 않다.
- 전체검색 시 폴더 결과와 링크 결과가 한 리스트에 섞이면 결과 문맥이 깨진다.
- 동일 링크가 여러 폴더에 존재할 때 결과를 어떻게 보여줄지 일관된 기준이 없다.
- 좌측 메인 검색과 우측 패널 검색의 역할이 겹치면 인터랙션이 혼란스러워진다.

<br>

## 3. 목표

### 3.1 사용자 목표

- 사용자가 폴더를 빠르게 찾을 수 있어야 한다.
- 사용자가 현재 선택한 폴더 안에서 링크를 빠르게 찾을 수 있어야 한다.
- 사용자가 전체검색을 통해 폴더와 링크를 한 번에 탐색할 수 있어야 한다.
- 사용자가 검색 결과에서 링크가 어떤 폴더들에 포함되어 있는지 즉시 이해할 수 있어야 한다.

### 3.2 제품 목표

- 검색 대상과 결과 구조를 명확히 분리하여 혼란을 줄인다.
- 현재 데이터 구조를 크게 깨지 않고 1차 버전을 빠르게 구현한다.
- 이후 전역 검색 고도화와 이벤트 로깅으로 확장 가능한 기반을 만든다.

<br>

## 4. UX 원칙

### 4.1 검색 경험 통일, 검색 범위 분리

검색창의 시각 스타일, 입력 방식, 아이콘, 인터랙션은 최대한 통일한다.  
다만 각 영역이 담당하는 검색 범위는 다음과 같이 분리한다.

| 영역 | 기본 역할 | 검색 대상 | 기본 범위 |
| :--- | :--- | :--- | :--- |
| 좌측 메인 검색 | 탐색 진입점 | 폴더, 링크 | 기본은 폴더 검색 |
| 우측 패널 검색 | 현재 작업 맥락 유지 | 링크 | 현재 선택된 폴더 내부 링크 |

### 4.2 기본값은 좁고, 확장은 명시적으로

좌측 검색은 기본적으로 `폴더만 검색`으로 시작한다.  
전체검색이 필요한 사용자를 위해 검색 범위 토글을 제공한다.

권장 범위 토글:

- `폴더만`
- `전체`

기본 선택:

- `폴더만`

선택 이유:

- `/my-links` 좌측 영역의 핵심 역할이 폴더 탐색이기 때문이다.
- 전체검색을 기본으로 두면 결과 해석 비용이 커진다.
- 우측 패널의 링크 검색과 역할이 겹치지 않도록 해야 한다.

<br>

## 5. 검색 범위 정책

### 5.1 좌측 메인 검색

좌측 검색창은 두 가지 모드를 가진다.

#### A. 폴더만 검색

- 폴더 이름 기준 검색
- 결과는 폴더 카드 또는 폴더 리스트로 표시
- 기존 폴더 탐색 흐름을 해치지 않는 범위에서 동작

#### B. 전체검색

- 검색어와 매칭되는 폴더 결과와 링크 결과를 모두 보여줌
- 단, 한 리스트에 섞지 않고 별도 섹션으로 분리
- 상단에 결과 탭 또는 칩으로 `전체 | 폴더 | 링크` 필터 제공 가능

### 5.2 우측 패널 검색

- 검색 대상은 링크만
- 검색 범위는 현재 `selectedFolderId` 기준으로 조회된 링크 목록
- 태그 필터, 정렬과 함께 사용 가능해야 함
- placeholder는 `Search links in this folder` 수준으로 명확화

<br>

## 6. 전체검색 결과 구조

### 6.1 핵심 정책

전체검색에서 검색어가 폴더와 링크 모두에 매칭되면 **둘 다 보여준다.**  
단, 결과를 한 리스트로 섞지 않고 다음과 같이 분리한다.

- `Folders`
- `Links`

이는 "전체검색을 켰다"는 사용자의 의도가 "어디 있든 관련 있는 것을 다 찾고 싶다"에 가깝기 때문이다.

### 6.2 결과 구성 예시

```text
[ 검색창: aaa ] [전체]

8 results
[All] [Folders 5] [Links 6]

Folders
- aaa 프로젝트              (폴더명 직접 매칭)
- aaa 참고자료              (폴더명 직접 매칭)
- Frontend                 (링크 'aaa 공식문서' 포함)
- Study                    (링크 'aaa 공식문서' 포함)
- Work                     (링크 'How to use aaa' 포함)

Links
- aaa 공식문서
  포함 폴더: Frontend / Study / Reference
- How to use aaa
  포함 폴더: Work / Archive
```

**주요 변경:**
- 링크에 포함된 폴더(Frontend, Study, Work 등)도 **Folders 섹션에 함께 표시**
- 폴더 클릭 시 우측 패널 링크 검색창에 검색어('aaa')가 자동 입력되어, 해당 폴더의 매칭 링크만 표시

### 6.3 UI 표현 규칙

- 검색창 바로 아래에 총 결과 수를 표시한다.
- 그 아래에 `All`, `Folders`, `Links` 탭 또는 칩을 둘 수 있다.
- `Folders` 섹션은 폴더 결과만 렌더링한다.
- `Links` 섹션은 링크 결과만 렌더링한다.
- 링크 카드 내부에 `포함 폴더` 메타정보를 표시한다.

### 6.4 결과를 섞지 않는 이유

- 폴더 결과와 링크 결과는 사용자가 기대하는 액션이 다르다.
- 폴더 결과는 "해당 폴더로 이동"이 주된 액션이다.
- 링크 결과는 "링크 열기" 또는 "링크가 저장된 위치 확인"이 주된 액션이다.
- 섞어서 보여주면 정보는 많아지지만 이해 비용이 크게 증가한다.

<br>

## 7. 링크 중복 및 포함 폴더 표시 정책

### 7.1 문제 상황

전체검색에서 동일한 링크가 여러 폴더에 저장될 수 있다. 예를 들어 동일 링크가 `Frontend`, `Study` 두 폴더에 모두 저장된 경우가 있다.

### 7.2 기본 정책

전체검색 결과에서 링크 카드에는 **해당 링크가 포함된 폴더를 모두 보여준다.**

- 링크 결과는 링크 자체의 정보와 함께 렌더링
- 링크 카드 내부에 `포함 폴더` 목록 표시
- 폴더 배지 클릭 시 해당 폴더로 이동 가능하도록 설계

### 7.3 폴더 표시 규칙

- 1~3개 폴더는 모두 바로 노출
- 폴더가 4개 이상이면 `+N more` 패턴 고려
- hover, 클릭, 확장 패널 등으로 전체 폴더 목록 확인 가능하도록 확장 가능

### 7.4 의미 분리

다음 두 정보는 같은 "폴더"처럼 보이지만 역할이 다르다.

- `Folders` 섹션의 폴더: 검색어에 직접 매칭된 검색 결과
- 링크 카드의 포함 폴더: 해당 링크가 저장된 위치 정보

따라서 반드시 위치를 분리해서 보여줘야 한다.

<br>

## 8. 데이터 및 API 설계 방향

### 8.1 현재 코드 기준 확인 사항

현재 프론트엔드에서는 북마크 조회 API가 `query` 파라미터를 받을 수 있다.

- `frontend/src/lib/api/bookmarkApi.ts`
- `frontend/src/lib/types/bookmark.ts`

또한 백엔드 `BookmarkSearchCommand`와 MyBatis 매퍼에서도 `query`를 받고 있다.

- `src/main/java/com/web/SearchWeb/bookmark/service/command/BookmarkSearchCommand.java`
- `src/main/resources/mapper/bookmark-mapper.xml`

단, 현재 매퍼 기준 링크 검색은 `display_title` 기준으로만 동작한다.

```sql
AND LOWER(msl.display_title) LIKE '%' || LOWER(#{query}) || '%'
```

반면 폴더 목록 API는 현재 검색 전용 파라미터가 없다.

- `frontend/src/lib/api/folderApi.ts`

따라서 1차 구현은 다음 전략이 현실적이다.

- 폴더 검색: 이미 로드된 폴더 목록 기반 클라이언트 필터
- 우측 링크 검색: 기존 `query` 파라미터 활용
- 전체검색 1차: 폴더는 클라이언트 필터, 링크는 서버 검색 조합

### 8.2 전체검색 결과 응답 방향

향후 전체검색을 서버 중심으로 고도화할 경우 아래 형태의 응답 구조를 권장한다.

```json
{
  "query": "aaa",
  "folders": [
    {
      "folderId": 1,
      "folderName": "aaa 프로젝트"
    }
  ],
  "links": [
    {
      "linkKey": "canonical-or-original-url",
      "title": "aaa 공식문서",
      "url": "https://example.com/aaa",
      "matchedBookmarkIds": [10, 25],
      "includedFolders": [
        { "folderId": 3, "folderName": "Frontend" },
        { "folderId": 7, "folderName": "Study" }
      ]
    }
  ]
}
```

### 8.3 링크 식별 기준

링크 중복 묶음 또는 관계 계산 시 권장 우선순위는 다음과 같다.

1. `canonicalUrl`
2. `originalUrl`
3. 필요 시 `linkId`

단, 1차 구현에서는 저장 단위가 북마크인 만큼 무리한 통합보다는 "링크 카드에 포함 폴더를 보여주는 방향"을 우선 적용한다.

## 9. 구현 단계 제안

### 9.1 1단계: 빠른 UX 정착

목표:

- 검색 범위를 명확히 나누고 기본 UX를 안정화

범위:

- 좌측 검색창 범위 토글 추가: `폴더만 | 전체`
- 좌측 `폴더만` 검색: 로컬 폴더 필터
- 우측 링크 검색: 현재 폴더 기준 `query` 연동
- placeholder 및 문구 정리

제외:

- 폴더와 링크를 동시에 묶는 서버 통합 검색 API
- 복잡한 dedupe 로직

### 9.2 2단계: 전체검색 결과 섹션화

목표:

- 전체검색에서 폴더와 링크를 동시에 보여주는 구조 도입

범위:

- 좌측 검색 결과 영역 추가
- `Folders` / `Links` 섹션 분리
- 결과 수 표시
- `전체 | 폴더 | 링크` 보기 필터 추가 가능

### 9.3 3단계: 포함 폴더 정보 고도화

목표:

- 링크 결과의 저장 위치를 명확히 보여줌

범위:

- 링크 카드 내 `포함 폴더` 배지 표시
- 폴더 배지 클릭 시 해당 폴더 컨텍스트 이동
- 폴더 수가 많을 때 축약 및 확장 UX 추가

### 9.4 4단계: 검색 품질 개선

목표:

- 검색 정확도와 탐색 속도 개선

범위:

- 링크 검색 범위를 `displayTitle` 외 `note`, `domain`, `tag`, `link title`까지 확장 검토
- 폴더 검색 API 또는 통합 검색 API 검토
- 디바운스, 캐싱, 최근 검색어, 키보드 탐색 추가

## 10. 프론트엔드 구성 제안

### 10.1 좌측 메인 영역

추가 상태 예시:

- `searchScope: 'folders' | 'all'`
- `searchQuery: string`
- `searchView: 'all' | 'folders' | 'links'`

렌더링 흐름:

- 검색어 없음: 기존 폴더 대시보드 유지
- 검색어 있음 + `폴더만`: 폴더 결과만 표시
- 검색어 있음 + `전체`: `Folders` / `Links` 결과 섹션 표시

### 10.2 우측 패널

추가 상태 예시:

- `linkSearchQuery: string`

렌더링 흐름:

- 현재 `selectedFolderId` 유지
- 정렬, 태그 필터와 함께 검색 적용
- 검색 상태에서도 폴더 컨텍스트를 잃지 않음

**폴더 클릭 시 자동 검색 입력 (신규):**

- 좌측 전체검색의 Folders 섹션에서 폴더를 클릭 시:
  ```typescript
  handleFolderClick(folderId) {
    bookmarkStore.setSelectedFolder(folderId);
    bookmarkStore.setLinkSearchQuery(currentSearchQuery); // 현재 검색어 자동 입력
  }
  ```
- 우측 패널 링크 검색창에는 `linkSearchQuery` 상태가 반영되어 미리 입력된 상태로 표시
- 사용자는 X 버튼으로 검색어를 삭제하거나, 새로운 검색어를 직접 입력 가능
- 다른 폴더를 클릭하면 `linkSearchQuery`는 새로운 검색어로 자동 업데이트됨

<br>

## 11. 이벤트 로깅 제안

검색 기능이 실제로 사용되는지 확인하기 위해 아래 이벤트를 추적한다.

| 이벤트 코드 | 설명 | 우선순위 |
| :--- | :--- | :--- |
| `SEARCH_EXECUTE` | 검색 실행 | P0 |
| `SEARCH_SCOPE_CHANGE` | `폴더만` / `전체` 범위 전환 | P0 |
| `SEARCH_RESULT_CLICK_FOLDER` | 검색 결과에서 폴더 클릭 (좌측 Folders 섹션) | P0 |
| `SEARCH_RESULT_CLICK_LINK` | 검색 결과에서 링크 클릭 | P0 |
| `SEARCH_CONTEXT_AUTO_INPUT` | 폴더 클릭 → 우측 패널 검색어 자동 입력 | P0 |
| `SEARCH_RESULT_CLICK_INCLUDED_FOLDER` | 링크 카드 내부 포함 폴더 클릭 | P1 |
| `SEARCH_VIEW_FILTER_CHANGE` | `전체 | 폴더 | 링크` 보기 전환 | P1 |

권장 속성 예시:

```json
{
  "query": "aaa",
  "scope": "folders | all | current_folder_links",
  "folder_result_count": 2,
  "link_result_count": 6,
  "selected_folder_id": 15
}
```

## 12. 검증 포인트

### 12.1 UX 검증

- 사용자가 좌측 검색과 우측 검색의 차이를 직관적으로 이해하는가
- 전체검색 결과에서 폴더와 링크가 섞이지 않아 이해가 쉬운가
- 링크 카드의 포함 폴더가 정보 과밀 없이 읽히는가

### 12.2 기능 검증

- `폴더만` 검색 시 폴더만 결과에 노출되는가
- `전체` 검색 시 폴더와 링크가 모두 노출되는가
- 우측 검색은 현재 선택된 폴더 범위를 벗어나지 않는가
- 링크가 여러 폴더에 저장된 경우 포함 폴더가 모두 표시되는가

### 12.3 성능 검증

- 검색 입력 시 불필요한 전체 재렌더가 과도하지 않은가
- 우측 패널 검색 시 API 호출 빈도가 과도하지 않은가
- 전체검색 결과 수가 많을 때 레이아웃 붕괴 없이 유지되는가

<br>

## 13. 비목표

이번 계획서 범위에서 바로 포함하지 않는 항목은 다음과 같다.

- 완전한 글로벌 검색 모달 별도 도입
- 고급 랭킹 알고리즘
- 자연어 검색
- 팀 폴더/팀 링크까지 포함한 통합 검색
- 모바일 전용 별도 검색 UX

## 14. 결론

`/my-links` 검색 기능은 "한 검색창으로 모든 것을 해결"하기보다, **좌측은 탐색, 우측은 현재 작업 컨텍스트 유지**라는 구조를 살려야 한다.

최종 방향은 다음과 같다.

- 좌측 검색 기본값은 `폴더만 검색`
- 좌측에서 필요 시 `전체검색`으로 확장
- 전체검색은 폴더와 링크를 모두 보여주되, 반드시 `Folders` / `Links` 섹션으로 분리
- 링크 결과에는 `포함 폴더`를 명시적으로 표시
- 우측 패널 검색은 현재 선택된 폴더 안의 링크 검색으로 유지

이 방향은 현재 코드 구조와도 잘 맞고, 1차 구현부터 단계적으로 확장하기에도 적합하다.
