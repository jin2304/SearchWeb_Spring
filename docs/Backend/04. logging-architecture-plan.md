# SearchWeb 통합 로깅 아키텍처 및 구현 계획

본 문서는 SearchWeb 서비스에서 발생하는 다양한 로그(사용자 행동 분석, 에러 디버깅, 보안 감사, 데이터 변경 이력)를 효율적으로 수집 및 관리하기 위한 **3대 축 로깅 아키텍처**와 **점진적 구현 로드맵**을 정의합니다.

---

## 1. 아키텍처 개요 (3대 축 로깅)

모든 로그를 각기 다른 서버나 복잡한 분석 도구로 구축할 경우 오버엔지니어링과 관리 비용 상승의 원인이 됩니다. 본 설계는 수집 목적과 데이터 형태에 따라 로깅 인프라를 **단 3개의 축**으로 단순화하여 구성합니다.

```text
[ 5가지 로그 요구사항 ]
    │
    ├── ① 외부 서비스 축 ──────> [ 구글 GA4 & GTM ]
    │                            └─ 수집 대상: GA4 분석 로그 (페이지뷰, 클릭 흐름 등)
    │                            └─ 특징: 프론트엔드에서 구글 서버로 직접 전송 (DB 저장 안 함)
    │
    ├── ② 애플리케이션 파일 축 ──> [ 서버 로컬 파일 (Logback) ] ──> Sentry (에러 분석 도구)
    │                            └─ 수집 대상: 버그 추격 및 에러 로그
    │                            └─ 특징: DB 저장 없이 파일로 관리, 에러 발생 시 슬랙 알림 연동
    │
    └── ③ 데이터베이스(DB) 축 ───> [ 서비스 DB (PostgreSQL) ]
                                 ├─ [ event_log 테이블 ]
                                 │    └─ 수집 대상: 비즈니스 KPI 로그 (가입 완료, 저장 완료 등)
                                 │
                                 └─ [ 엔티티 & *_history 테이블 ]
                                      └─ 수집 대상: 감사 로그 (JPA Auditing 활용)
                                      └─ 수집 대상: 변경 이력 로그 (과거 스냅샷 저장)
```

---

## 2. 축별 상세 설계

### ① 외부 서비스 축 (GA4 & GTM)
* **목적**: 마케팅 성과 측정, 사용자 유입 채널 분석, 서비스 내 주요 UI 클릭(퍼널) 분석
* **수집 대상**: `page_view`, `scroll`, `session_start`, `first_visit`, 버튼 클릭 등
* **구현 방식**: 
  * 백엔드 서버를 거치지 않고 프론트엔드(Next.js)에서 직접 구글 서버로 전송합니다.
  * `src/lib/analytics.ts` 헬퍼 모듈을 구현하여 클라이언트 이벤트를 발송합니다.
  * 개발 환경의 테스트 트래픽이 운영 데이터에 유입되는 것을 방지하기 위해 GA4 내부의 **개발자 트래픽 필터(Developer Traffic Filter)** 또는 **GTM/GA4 컨테이너(측정 ID) 분리 정책**을 적용합니다.

### ② 애플리케이션 파일 축 (Logback / Sentry)
* **목적**: 시스템 오류 모니터링, API 호출 결과 디버깅, 성능(느린 쿼리 등) 추적
* **수집 대상**: 런타임 예외(Exception), 에러 스택 트레이스(Stack Trace), 외부 API 타임아웃 등
* **구현 방식**:
  * 비즈니스 분석용이 아니므로 절대 데이터베이스(RDB)에 적재하지 않습니다.
  * Spring Boot 내장 로깅 시스템인 **SLF4J + Logback** 설정을 활용하여 콘솔 및 로컬 텍스트 파일(`app.log`)로 기록합니다.
  * 운영 환경 배포 후에는 **Sentry(센트리)**를 연동하여 `ERROR` 등급의 로그만 실시간으로 수집하고 슬랙(Slack) 등의 메신저 알림으로 즉시 개발팀에 공유되도록 설정합니다.

### ③ 데이터베이스(DB) 축 (PostgreSQL)
* **목적**: 비즈니스 핵심 KPI 지표 산출, 보안 및 관리자 감사, 데이터 복구를 위한 변경 이력 추적
* **구현 방식**: 데이터의 성격에 따라 물리적으로 테이블을 분리하여 설계합니다.

#### A. KPI 이벤트 로그 (`event_log` 테이블)
사용자 행동 데이터의 흐름을 기록하는 단 하나의 공통 로그 적재용 테이블입니다. 실데이터와 분리되어 누적만(Append-only) 일어납니다.

```sql
CREATE TABLE event_log (
    id                 BIGSERIAL PRIMARY KEY,
    member_id          BIGINT NOT NULL,
    event_type         VARCHAR(50) NOT NULL,    -- 'bookmark_saved', 'search' 등
    event_properties   JSONB DEFAULT '{}',       -- 이벤트별 정밀 파라미터 유연하게 저장
    session_id         VARCHAR(100),
    page_url           VARCHAR(500),
    created_at         TIMESTAMP NOT NULL DEFAULT NOW(),
    
    CONSTRAINT fk_event_member FOREIGN KEY (member_id) REFERENCES member(member_id)
);

CREATE INDEX idx_event_log_type_created ON event_log (event_type, created_at);
```

#### B. 감사(Audit) 및 변경 이력(History) 로그
데이터의 변경 시각, 수정 주체, 수정 전 과거 값을 관리합니다.

1. **감사(Audit)**:
   * 별도의 이력 테이블을 두지 않고, 주요 엔티티 테이블(예: `member`, `bookmark`)에 직접 컬럼을 포함시킵니다.
   * Spring Data JPA의 **Auditing 기능**(`@CreatedDate`, `@CreatedBy`, `@LastModifiedDate`, `@LastModifiedBy`)을 사용해 데이터 등록/수정 시 자동으로 값이 입력되도록 합니다.
2. **변경 이력(History)**:
   * 주요 비즈니스 데이터(예: 북마크 상세 내용, 폴더 구조 등)가 수정되거나 삭제될 때 복구 및 추적이 가능하도록 엔티티별 백업 테이블을 생성합니다.
   * *예: `bookmark_history` 테이블*
     ```sql
     CREATE TABLE bookmark_history (
         history_id  BIGSERIAL PRIMARY KEY,
         bookmark_id BIGINT NOT NULL,
         old_title   VARCHAR(255),
         old_note    TEXT,
         changed_at  TIMESTAMP NOT NULL DEFAULT NOW()
     );
     ```

## 3. 점진적 구현 로드맵

급격한 인프라 도입 대신 프로젝트 성장 속도에 맞춰 순차적으로 기능을 구현해 나갑니다.

### Phase 1 (현재 단계): 클라이언트 로깅 안정화
* **프론트엔드**: GA4/GTM 태그 연동 완료 및 UI 클릭 이벤트 트래킹 코드 안정화.
* **백엔드**: 추가 개발 없이 기본 Logback 설정만을 통해 파일 로그로 서버 모니터링 수행.

### Phase 2 (차기 단계): 백엔드 DB 적재 및 비동기 처리
* **DB 구축**: `event_log` 및 주요 엔티티의 `*_history` 테이블 설계 및 DDL 실행.
* **백엔드**: API 로직 수행 시 성능 저하를 방지하기 위해 `@Async` 어노테이션이나 이벤트 리스너(ApplicationEventPublisher)를 이용해 비동기 방식으로 `event_log`에 이벤트를 적재하는 기능 구현.
* **프론트엔드**: 웹 브라우저의 트래픽을 모아 서버의 배치 API(`/api/events/batch`)로 쏘아 `event_log`에 통합 적재하는 파이프라인 추가.

### Phase 3 (배포 이후): 실시간 모니터링 보완 및 고도화
* **모니터링**: 운영 서버에 Sentry를 적용하여 서버 런타임 버그 발생 시 슬랙 즉시 알림 설정.
* **통계 집계**: `@Scheduled` 기능을 활용해 매일 새벽 `event_log` 테이블을 집계하고, 일별 KPI 스냅샷 테이블(`kpi_daily_snapshot`)에 통계를 누적하여 어드민 대시보드 페이지 구현 기반 마련.
